# 祈使句提交规范

让 Git 提交标题（subject 行）读起来像一条命令：用 `添加功能` 而不是 `添加了功能`。正文的书写规范不在本技能范围内。

## 适用场景

- 执行 `git commit` 前——撰写提交标题时
- 审查或校验已有提交信息
- 修正评审或 CI 中被驳回的提交信息
- 解答关于提交信息规范的疑问

## 工作流程

### 第 1 步：应用三条规则

这些规则适用于**所有**提交标题，即使仓库历史使用了其他风格——统一正是本技能的目的。

1. **祈使语气、动词原形** —— 用 `Add`、`Fix`、`Update`；不用 `Added`、`Fixes`、`Updating`。标题必须能补全句子*"如果应用这个提交，它将 ______"*：`Add login validation` 通顺；`Added login validation` 不通顺。Git 自身就是这样写的——`git merge` 生成 `Merge branch 'x'`，`git revert` 生成 `Revert "..."`。
2. **首字母大写** —— 仅适用于拉丁字母书写的标题；其他语言没有大小写。
3. **不以句号结尾** —— 标题末尾不加句号。

### 第 2 步：检验并修正

把最终标题填入*"如果应用这个提交，它将 ______"*。通顺则继续；不通顺则改写，并说明修改了哪些标题以及原因。

## 正确 vs 错误

| ✅ 正确 | ❌ 错误 |
|---------|----------|
| `Add login validation` | `added login validation` |
| `Fix memory leak` | `Fixes memory leak.` |
| `Update README` | `Updating README` |

## 与约定式提交的区别

约定式提交与祈使句提交是两种不同规范。本技能强制采用祈使句风格：写 `Add login`，不写 `feat: add login`，且同一条标题中不可混用两者。

## 禁止事项

- 不要书写或接受非祈使句的标题——包括为了迎合周边历史而妥协；本技能定义的就是必须遵守的规范。
- 不要在同一条标题中混用两种规范：`feat: Added login` 两者都不满足。

## 无法确定时

默认套用三条规则；*"如果应用这个提交，它将 ______"* 检验可以裁定措辞上的边界情况。仅当用户对某条提交明确要求其他风格时才可偏离——明确指示优先于本技能。
