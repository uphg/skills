# 重构指南 —— 增量迁移

边交付功能边增量迁移。大爆炸式重写会停掉业务开发并失去管理层支持；违背团队意愿的强制推行只会得到一个没人遵守的形式化结构。

## 门控问题

只有满足至少一条才值得迁移——否则当前架构运转正常，不该动：

1. 新成员抱怨难以达到生产力。
2. 改一处经常弄坏不相关的另一处。
3. 因为要跟踪的东西太多，加功能变得困难。

开工前先说服团队（绝不以 leader 身份强压），并让管理层认同：增量迁移不停业务、文档化的标准架构加快新人上手、团队不用再维护私有架构文档。

## 五个阶段

一次性准备：加 `@` → `./src` 别名，后续顶层移动就不用改写所有 import。

### 阶段 1：按页面划分
建 `pages/`；把组件代码从路由文件移进页面文件夹并提供 `index.js`。路由变成薄适配层（`export { ProductPage as default } from "@/pages/product"`）。**仅本阶段**容忍页面间互相导入。

### 阶段 2:把其余代码与页面分离
二元分类：导入了 pages/routes 的代码 → 顶层（`app`）；其余全部 → `shared`。

### 阶段 3：消灭页面对页面的导入
对每条残留的 page→page 导入：展示性/配置性代码且可能各自演化 → 复制粘贴；真正通用 → 提升到 `shared`（UI kit → `shared/ui`，常量 → `shared/config`，后端调用 → `shared/api`）。绝不复制业务逻辑——bug 修复必须只落一处。

### 阶段 4：重新拆包 shared
找出只有一个页面在用的对象，移回那个页面的模块——包括 actions、reducers、selectors。共置优于"把所有 actions 放一起"。shared 是其他每一层的依赖，必须保持小而真实复用。

### 阶段 5：按技术目的组织
把每个模块拆成目的文件夹：`ui/`、`api/`、`model/`（store、schema、业务逻辑）、`lib/`、`config/`。按下表溶解遗留文件夹。

仅在触发条件满足时的可选后置阶段：
- 把跨多个页面复用的业务逻辑模块提取到更低业务层。
- 打造干净的、无业务语境的 `shared/ui`：内部不含业务逻辑；把逻辑向上提取，或在用量稀少处直接复制。

## 遗留目录映射

| 遗留 | 去向 |
|---|---|
| `routes/`、`screens/`、`views/` | 薄文件留在路由；内容 → `pages/<name>/ui` |
| `components/`、`containers/` | 向上提取业务逻辑后大多 → `shared/ui` |
| `helpers/`、`utils/` | 按功能分组 → `shared/lib` |
| `constants/` | 按功能分组 → `shared/config` |
| `actions/`、`reducers/`、`selectors/`（单页） | 该页面的 `model/` |
| 同上但被跨页复用 | 业务层 / feature 模块 |
| `modules/`（业务逻辑） | feature 层模块；大型 UI 块留在页面附近 |
| `services/`、`api/` | `shared/api` 或所属模块的 `api/` |

## 迁移反模式

- **大爆炸重写** —— 停掉业务、失去支持；永远增量。
- **目的文件夹按产物类型命名** —— 在模块里建 `components/`、`types/`、`utils/` 只是把 smell 搬了个家。
- **臃肿的 shared** —— 单用途 state/actions 全倒进去，让风险最高的依赖更危险。
- **复制业务逻辑** —— 仅展示性/配置性代码可以复制。
- **继承细粒度提取** —— 单消费者模块通常是噪音；先合并回它的消费者。
