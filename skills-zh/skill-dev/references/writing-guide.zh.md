# 写作指南

关于技能编写中两个高杠杆方面的深入指导：`description` 字段（决定触发）与正文写作风格。

## Description 优化

frontmatter 的 `description` 会在每个会话中作为可用技能列表的一部分展示给模型。模型仅凭这段文字决定是否查阅技能，因此它是整个技能包中杠杆最高的一行。

### 触发机制实际上如何运作

- 在模型决定加载技能之前，它只能看到 `name` + `description`。
- 模型倾向于**漏触发**（under-trigger）：明明有帮助却跳过技能。略微"pushy"的 description 可以对冲这一点。
- 简单的一步式任务即使 description 完美匹配也可能不触发任何技能——模型直接自己处理。因此 description 应瞄准实质性的、多步骤的或专业化的工作。
- 过度触发同样存在：堆满通用关键词的 description 会在相邻但错误的任务上触发，浪费上下文。

### 设计触发评估查询

要客观测试或调优 description，写约 20 条真实查询，分为 should-trigger 和 should-not-trigger 两组：

```json
[
  {"query": "...", "should_trigger": true},
  {"query": "...", "should_trigger": false}
]
```

**Should-trigger 查询（8–10 条）：**

- 覆盖同一意图的不同措辞——正式的和口语的都要有。
- 包含用户从未点名该技能或其领域、但明显需要它的场景。
- 包含不常见用例，以及该技能与其他技能竞争但应该胜出的场景。
- 要具体：文件路径、项目背景、列名、听起来真实的来龙去脉。长短混合；允许错别字和缩写。

差：`"写一个 Vue 组件"`
好：`"我们组件库里那个 Select 的 props 快 20 个了，新同事又要加一个 loading 态，帮我按库里的规范理一下 API，顺便看看 emits 是不是该拆"`

**Should-not-trigger 查询（8–10 条）：**

- 近似情况（near-miss）才是有价值的——共享关键词或领域、但实际需要别的东西的查询（相邻框架、不同任务类型）。
- 避免明显无关的反例（"写个斐波那契"）——测不出任何东西。

如果需要迭代 description：在全部查询上评估每个候选版本，选择在 should/should-not 平衡上表现最好的一个，并通过保留一部分查询不参与改进循环来防止过拟合。

### Description 快速改写流程

1. 给每处能力描述画线——*做什么*是否在第一句话就说清了？
2. 数一数触发场景——少于 3 个？从真实用户语言中补充措辞。
3. 检查是否混入了使用说明——把它们移到正文。
4. 以竞争技能的视角重读——它会抢走这个触发吗？用更具区分度的名词收紧表述。

## 正文写作风格

### 解释 why

对比：

弱（光秃秃的规则）：

```markdown
组件文件中绝不使用默认导出。
```

强（规则 + 理由）：

```markdown
组件使用具名导出：打包器对具名导出的 tree-shaking 更可靠，
编辑器自动导入解析无歧义，而且改名遗漏会表现为导入错误，
而不是运行时的静默 `undefined`。
```

第二个版本让模型能把*理由*应用到规则从未提及的场景。硬性禁止只留给那些无论上下文如何都错误的事。

### 从反馈泛化

当评审说"这个输出不对"时，修复的是这一类问题，而不是这个实例：

1. 问是什么误解导致了错误输出。
2. 判断修复手段应是新的解释、更好的示例、结构调整还是脚本。
3. 优先选解释而非特例枚举——枚举会无限膨胀。

一个有用的检验：想象这个技能被用于一条你从未见过的提示词。你的修复还有帮助吗？

### 保持提示词精炼

正文的每一行都会在技能每次被触发时被读取。审计以下内容：

- 从未有测试运行为之受益的章节 → 删除。
- 模型本来就会自发去做的事的指令 → 删除。
- 重复的告警 → 在正确的位置说一次即可。

如果删掉什么感觉有风险，请记住：更短的技能触发更快的推理和更少的漂移；冗长是成本，不是保险。

### 示例模式

具体的输入/输出对照是传授风格的高效方式：

```markdown
## 提交信息格式
**示例 1:**
输入: Added user authentication with JWT tokens
输出: feat(auth): implement JWT-based authentication
```

保持示例具有代表性而非病态案例——模型会模仿它们看到的形态。
