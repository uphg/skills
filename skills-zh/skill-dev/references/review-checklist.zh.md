# 技能审查清单

发布新技能或重大修改之前，逐节过一遍。每一条都设计为可用"是/否"回答。

## 1. 触发（frontmatter）

- [ ] `name` 与目录名一致，为 `kebab-case`。
- [ ] `description` 同时说明**技能做什么**和**何时使用**。
- [ ] `description` 包含至少 3 个具体触发场景（"当……时使用"）。
- [ ] `description` 提及用户实际会输入的领域名词。
- [ ] `description` 为 1–3 句话，没有把使用说明泄漏进去。
- [ ] 已考虑近似情况（near-miss）：description 是否能避免在相邻但错误的任务上误触发？如果触发准确率很重要，应设计 should-trigger / should-not-trigger 评估查询（见 writing-guide.md）。

## 2. 渐进披露

- [ ] `SKILL.md` 正文在 500 行以内。
- [ ] 最重要的指导出现在正文前半部分。
- [ ] 详细/偶尔才需要的材料放在 `references/` 中，而不是内联。
- [ ] 每个参考文件都在正文中留有指针，说明*何时*阅读它。
- [ ] 超过 300 行的参考文件包含目录。
- [ ] 确定性重复步骤已放入 `scripts/`（如适用）。
- [ ] 输出模板 / 静态资源放入 `assets/`（如适用）。

## 3. 写作风格

- [ ] 指令使用祈使句。
- [ ] 规则附带理由（"做 X 因为 Y"）而非光秃秃的 MUST；全大写的 ALWAYS/NEVER 很少或不存在。
- [ ] 指导内容能泛化到催生它的那些具体示例之外。
- [ ] 快速参考数据用表格；流程用编号步骤；场景用 bullet 列表；目录树/命令用代码块。

## 4. 结构

- [ ] 遵循默认骨架（When to Use / Workflow / 其他章节），`Prohibitions` 和 `When Unsure` 只在有价值时保留。
- [ ] Workflow 步骤有编号，顺序即 agent 实际执行的顺序。
- [ ] 各章节之间没有矛盾。

## 5. 评估

- [ ] 存在 2–3 条真实的测试提示词（`evals.json` 或 PR 描述），每条都有预期结果。
- [ ] 测试提示词实际针对技能运行过，或用户明确选择跳过。
- [ ] 对产出主观的技能，结果已由用户做过定性评审。

## 6. 宿主集成

- [ ] 若宿主集合维护来源元数据（`GENERATION.md`）或变更日志（`CHANGES.md`），已创建或更新。
- [ ] 变更日志条目说明了改了什么、为什么改。
- [ ] 任何列出可用技能的索引、目录清单或 README 已更新，包括安装命令（如适用）。
