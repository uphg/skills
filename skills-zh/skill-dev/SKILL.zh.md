# 技能开发

一套用于设计、编写、测试和维护高质量技能包的方法论——涵盖意图捕获、包结构设计、description 优化、评估与仓库集成。

## 何时使用此技能

- 从零创建新的技能包
- 编辑、重构或重组现有技能
- 改进技能的 `description` frontmatter 以提升触发准确率
- 在发布前或修改后审查技能质量
- 为技能添加测试提示词 / 评估以验证其有效性

## 核心原则

这些原则解释了技能"为什么这样写"。请在每一步中贯彻它们。

### 1. 渐进披露 —— 上下文是稀缺资源

技能分三层加载，每一层都要有意设计：

| 层级 | 内容 | 加载时机 | 预算 |
|---|---|---|---|
| 1 | frontmatter 的 `name` + `description` | 始终（每个会话） | ~100 词 |
| 2 | `SKILL.md` 正文 | 技能被触发时 | 500 行以内 |
| 3 | 捆绑资源（`references/`、`scripts/`、`assets/`） | 按需加载 | 无限制；脚本可不加载直接执行 |

这就是为什么 `description` 决定一切（第 1 层必须赢得触发机会），也是为什么详细材料应放进 `references/` 而不是撑大正文。

### 2. 解释 why，而非堆砌 MUST

现代 LLM 推理能力很强。一条附带理由的指令（"做 X，否则 Y 会出问题"）能泛化到作者没预料到的场景；光秃秃的 `ALWAYS`/`NEVER` 不能。如果发现自己在写生硬的全大写规则，请重新表述：解释不这样做会出什么问题。硬性禁止只留给那些真正在任何情况下都错误的事。

### 3. 泛化，而非过拟合

一个技能会在未来无数提示词中使用，但你只基于少数几个例子迭代。修复反馈时问一句"这个修复能否泛化？"针对单个例子的琐碎补丁是过拟合；更好的解释、比喻或模式则惠及未来每一次使用。

### 4. 确定性部分脚本化

如果技能的每次执行都会重复同样的机械步骤（脚手架文件、校验结构、生成样板代码），就把这些逻辑写一次放进 `scripts/`，让技能调用它。未来每次运行都能省下重复造轮子的 token 和错误。

## Workflow

### Step 1: 捕获意图

动笔之前先回答这些问题。如果用户说"把这个变成技能"，优先从当前对话历史中提取答案；只让用户填补缺口：

1. 这个技能要让 agent 能做什么？
2. 什么时候应该触发？（用户的话术、场景、近似情况）
3. 触发后的预期输出 / 行为是什么？
4. 技能的产出是否可客观验证（文件转换、固定流程）？如果是，在 Step 5 准备测试提示词；如果产出是主观的（写作风格），则依赖人工评审。

### Step 2: 设计包结构

每个技能都是一个自包含的目录，目录名与其用途一致：

```
<skill-name>/
├── SKILL.md          # 技能定义（必需）
│   ├── YAML frontmatter（必须有 name、description）
│   └── Markdown 指令正文
└── 捆绑资源（可选）
    ├── references/   # 按需加载的详细文档
    ├── scripts/      # 确定性/重复任务的可执行代码
    └── assets/       # 用于输出的文件（模板、图标、字体）
```

- 技能目录名：`kebab-case`，与 frontmatter 的 `name` 一致。
- 父目录取决于宿主环境（个人技能目录如 `~/.claude/skills/`、项目级 `.agents/skills/`，或精选技能集合仓库）。包内其他内容不假设任何特定位置。
- 部分宿主或集合会叠加额外约定（如来源元数据 `GENERATION.md`、变更日志、技能目录清单）；存在时遵循即可，它们不属于技能格式本身。
- 当技能支持多个领域/变体时，按变体组织，使模型只读取相关文件：
  ```
  <skill-name>/
  ├── SKILL.md         # 工作流 + 变体选择
  └── references/
      ├── aws.md
      └── azure.md
  ```

### Step 3: 编写 Frontmatter 和 Description

`description` 是首要的触发机制——渐进披露的第 1 层。它必须同时包含**技能做什么**和**何时使用**，列出具体的触发场景。措辞可以略微"pushy"：模型倾向于漏触发（under-trigger），所以要提及用户可能说到但不会直呼其名的相邻表述和相关关键词。

**弱**（只有功能，没有触发场景）：

```yaml
description: "Vue 组件库开发规范。"
```

**强**（功能 + 时机 + 触发场景）：

```yaml
description: "Vue 3 组件库编写规范。当编写或评审组件库组件、设计 props/emits/slots API、在 JSX 中权衡 emits 与回调 props、或组织组件库的测试与 hooks 时使用。"
```

经验法则：

- 一到三句话；功能前置。
- 包含 3 个以上具体触发场景（"当……时使用"）。
- 提及用户实际会输入的关键领域名词。
- 不要把使用说明写进 description——那属于正文。

### Step 4: 编写正文

以下面的骨架为默认结构，只保留真正有价值的章节：

```markdown
# <技能标题>

<一行概述。>

## 何时使用此技能
<具体的触发场景 bullet 列表。>

## Workflow
<编号步骤；流程性内容用 ### Step N: 小标题。>

## <其他章节>
<快速参考表格、决策流程、代码示例。>

## Prohibitions          ← 仅在存在硬性规则时保留
## When Unsure           ← 仅在存在合理兜底行为时保留
```

格式约定：

- **表格**用于快速参考数据（映射关系、选项、命名）。
- **编号步骤**用于流程指引；**bullet 列表**用于场景和约束。
- **代码块**用于目录树和命令。
- 把最重要的指导放在前面——假设后半部分可能永远不被读到。

写作风格：

- 使用祈使句（"运行 X"、"把 Y 放到 Z"）。
- 就地解释理由（原则 2）。
- 正文保持在 500 行以内；接近上限时把细节移入 `references/`，并留下指针说明*何时*应阅读各参考文件。超过 300 行的参考文件应包含目录。

### Step 5: 编写测试提示词

写 2–3 条真实可信的测试提示词——真实用户会说的话，而不是抽象概括——并记录预期结果。保存为 `evals.json` 放在技能旁（若仓库偏好也可放在 PR 描述中）：

```json
{
  "skill_name": "<skill-name>",
  "evals": [
    {
      "id": 1,
      "prompt": "以用户的口吻描述的任务提示词",
      "expected_output": "正确结果应该是什么样的"
    }
  ]
}
```

好的提示词足够具体和实质，能让模型真正从查阅技能中受益。然后运行它们（直接运行或通过子代理），将输出与 `expected_output` 对照。对于产出主观的技能，把结果交给用户做定性判断，而不是强行加断言。

### Step 6: 对照清单审查

定稿前，逐项过一遍 [references/review-checklist.zh.md](references/review-checklist.zh.md) 中的质量清单，涵盖触发、渐进披露、写作风格、结构、评估与宿主集成。

关于 description 优化（should-trigger / should-not-trigger 查询设计、near-miss 反例）和写作风格模式的更深入指导，见 [references/writing-guide.zh.md](references/writing-guide.zh.md)。

### Step 7: 完成集成

根据技能最终所在位置的约定适配（个人技能目录、某个项目，或精选技能集合仓库）：

1. 如果宿主维护来源元数据（如 `GENERATION.md`）或变更日志（如 `CHANGES.md`），创建或更新它们。
2. 更新任何列出可用技能的索引、目录清单或 README，包括安装命令（如有）。
3. 最后再完整过一遍发布检查清单。

## 快速参考

| 决策点 | 规则 |
|---|---|
| 目录 / 技能名 | `kebab-case`，与 frontmatter `name` 一致 |
| description 内容 | 功能 + 3 个以上触发场景，略偏 pushy |
| 正文长度 | 500 行以内；超出的部分移入 `references/` |
| 确定性重复步骤 | 移入 `scripts/` |
| 输出模板 / 字体 / 静态文件 | 放入 `assets/` |
| 包位置 | `<任意父目录>/<skill-name>/`；父目录取决于宿主环境 |
| 硬性 MUST / 全大写规则 | 避免；改为解释 why |
| 验证 | 测试提示词 + 审查清单 |

## Prohibitions

- 不得创建内容会超出用户陈述意图而令人意外的技能（恶意软件、漏洞利用代码、数据外泄工具）。
- 不得把使用说明或长表格塞进 `description` 字段。
- 不得让 `SKILL.md` 通过内联本应属于 `references/` 的材料膨胀到 ~500 行以上。
- 不得编写只修补特定测试示例而不考虑泛化的修复。

## When Unsure

- 某章节是否需要 → 省略它；出现真实需求再加回。
- 材料是否值得放入 `references/` → 模型只是偶尔需要的，放；始终需要的，留在正文。
- 测试该多严格 → 默认 2–3 条带预期记录的测试提示词，由用户决定是否需要更深入的评估。
